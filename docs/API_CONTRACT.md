# API Contract — ElProof

> Endpoint list and request/response formats. Conventions: `.claude/rules/api-standard.md` +
> [`knowledge/API_GUIDE.md`](../knowledge/API_GUIDE.md). All paths are under `/api/v1`, with one exception:
> the payment gateway's callback `POST /webhooks/payment` has **no** `/api/v1` prefix (see `payment` below).
> Auth header required on every endpoint except the ones marked *public* (see API_GUIDE.md).
>
> Last brought in line with `apps/api` on 2026-11-10 (UI revamp, ADR-0032…ADR-0036, including the late decision that
> `If-Match` is **required** on field edits). The route-by-route inventory, with who may call each route and whether
> `apps/web` still does, is [`docs/plan/revamp-ui-shadcn/API-INVENTORY.md`](plan/revamp-ui-shadcn/API-INVENTORY.md).

## Shared conventions

Everything in this section applies to every endpoint below unless a row says otherwise; the sections named in
parentheses hold the details.

- **Principals and auth.** `Authorization: Bearer <accessToken>`. Four principal types: `platform_admin` (ElProof's own
  team, **two-factor mandatory**: until the session is a TOTP session every route except `auth/me` and `auth/mfa/setup|enable`
  answers 403 `mfa_required`), `staff` (a WO's team), `client` (bride/groom/family — **GET only**, on a fixed allowlist, see *Client
  Portal*) and `app` (an external application, minted by `POST /auth/app/token`, only for `/external/*`). Tenant, role and
  permissions always come from the token, never from a request parameter. Staff and client access is decided by the permission keys
  of the person's workspace role (ADR-0026): a row that says `project.edit` means "a role holding that key"; names such as Owner,
  Admin or Wedding Planner are only the default role templates. A staff role whose project scope is *assigned* reaches only the
  projects where the person is PIC or PIC Sales (403 on any other project; narrower lists, never a 403 on a list).
- **Envelope.** Success `{ "success": true, "message": "...", "data": ... }`; error `{ "success": false, "message": "...", "errors": ... }`.
  Mutations of project data answer with the item exactly as its list shows it, plus `projectProgress` (and `ledgerSummary` on
  payments) — see *Tahap 5*.
- **Errors per field.** A validation failure is **422** with `errors: { "<field>": ["message", ...] }`, *all* problems at once, the
  key being the JSON field name (`eventDate`), a row of an array (`terms[2].amount`, `evidence[0].uploadToken`) or a header
  (`Idempotency-Key`, `If-Match`); `message` is the first problem, followed by "Ada N isian lain yang perlu diperbaiki." when there
  are more. `errors.code` is an additive machine-readable reason where one exists (`forbidden_permission`, `forbidden_role`,
  `payment_exceeds_contract`, `invalid_status_transition`, `trial_limit_reached`, `rate_limited`, `idempotency_key_reuse`, `upload_token_used`,
  `presign_unavailable`, `mfa_required`, `link_invalid`, …). Other statuses: 400 body is not valid JSON / not an object (or a malformed
  header), 401 no or dead session, 403 not allowed, 404 not found *or another workspace's* (never 403 for a row you may not know exists),
  405, 409 conflict, 413 file too large, 428 precondition required, 429 rate limited (with `Retry-After`).
- **Pagination.** Every list marked *paginated*: `?page=&limit=` (default 1 / 10, `limit` capped at 100) and
  `meta: { page, limit, total, total_pages }` next to `data`. Some tenant-scoped pickers still accept `?all=true` (plain array, no `meta`),
  each bounded by one workspace; the Platform Console lists never do. `?search=` (alias `?q=`, `q` wins) is a `LIKE` match on columns that
  vary per endpoint; every other filter is applied in SQL too, so search + filter + page combine correctly.
- **Sorting.** `?sort=field:asc|desc` on every paginated list that has a whitelist (*Tahap 6*): one column, the primary key as the last
  tie-breaker, empty values last; a field outside the whitelist is **422** `errors.sort`. The effective order is echoed as
  `meta.sort` (`"remaining:desc"`); lists without sorting have no `meta.sort`.
- **`Idempotency-Key`** (header, optional) on `POST /projects` and the three payment `POST`s: 8–128 characters of `[A-Za-z0-9_-]`; the same key
  with the same body replays the stored 2xx answer (`Idempotent-Replay: true`), a different body is 422 `idempotency_key_reuse`, the same request
  still running is 409 `idempotency_in_progress` (*Tahap 4*).
- **Versions: `updatedAt`, `ETag`, `If-Match`, 409, 428.** Every item of a project, project milestone, project vendor, vendor milestone, kendala,
  client/vendor/venue payment and evidence file carries `updatedAt` (RFC 3339, six fractional digits, UTC, e.g. `2026-11-10T08:15:30.123456Z`),
  and every single-item answer of these also sets the header `ETag: "<updatedAt>"`. A `PATCH` sends that value back as `If-Match` (quotes optional).
  **`If-Match` is required — 428 `Precondition Required`, `errors: {"If-Match": ["wajib"]}`, nothing written — on every field-editing `PATCH` of a project,
  project milestone, project vendor, vendor milestone, kendala, client payment, vendor payment and venue payment.** It stays optional (honoured when sent)
  for a project `PATCH` whose body is *only* `isArchived`, and for the evidence `PATCH {isClientVisible}`; the five directory `PATCH {isActive}` calls ignore it.
  A malformed value is 400 (`errors["If-Match"]`). A write is a compare-and-set on the version; when the row moved on it is **409**
  `{ success:false, message:"Data ini sudah diubah orang lain. Muat ulang untuk melihat versi terbaru.", errors:{"_conflict":["stale"]}, data:{ current: <the item as it is now> } }`
  (no `ETag`); a row that does not exist (or is another workspace's) stays 404, with or without the header (*Tahap 8*).
- **Partial PATCH and explicit state.** `PATCH` changes only the keys present (`null` clears only where documented as nullable). State is set, never toggled:
  `{"isArchived": bool}` on a project, `{"isClientVisible": bool}` on an evidence file, `{"isActive": bool}` on vendor, venue, vendor category, client and staff — repeating
  a state is a 200 no-op. The seven old `toggle-*` routes no longer exist (404). The Platform Console's own toggles (`toggle-suspension`, plan / payment-App / platform-admin
  `toggle-active`) are unchanged.
- **Soft delete and restore.** Deleting a client payment, vendor payment, venue payment, vendor engagement or client is **200** `{ id, restorableUntil, … }`
  and reversible for 24 hours with `POST …/restore`; a purge job hard-deletes after that (*Tahap 5*). Other deletes (project, staff, vendor, venue, vendor category,
  milestone template, evidence file) are permanent.
- **Signed uploads.** A file is sent in two steps: `POST /projects/{id}/uploads {fileName, mimeType, size}` returns `{uploadToken, method:"PUT", url, headers, expiresAt, direct}`;
  the browser PUTs the bytes to `url` (object storage when `direct`, otherwise `PUT /projects/{id}/uploads/{token}` on this API), then names `uploadToken` in
  the payment request, which records payment and proof in one transaction (*Tahap 4*). The older base64 `POST /projects/{id}/evidence` keeps working.

## `identity`

| Method | Path | Notes |
|---|---|---|
| POST | `/auth/login` | *public*; rate limited per IP (429 `rate_limited`, `Retry-After`). body `{username, password}` — `username` accepts either a real username or an email; tried as username first, then as email (against every credential sharing that email, since email isn't unique the way username is — see ADR-0005) → a session `{accessToken, refreshToken, principalType, principalId, tenantId, role, displayName, mfa, mfaSetupRequired}`, **or**, when the account has two-factor on, `{mfaRequired: true, mfaToken}` to be answered at `/auth/mfa/verify`. `mfaSetupRequired` is true for a platform admin who has not enrolled yet |
| POST | `/auth/refresh` | *public*. body `{refreshToken}` → a new session (same shape as login), rotates the old refresh token |
| POST | `/auth/logout` | *public*. body `{refreshToken}`; revokes the refresh token; always 200 |
| GET | `/auth/me` | any authenticated principal — the caller's token claims. The one route a platform admin without two-factor may still call (besides `mfa/setup\|enable`) |
| POST | `/auth/mfa/verify` | *public*, rate limited like login. body `{mfaToken, code}` (6-digit TOTP) → a session with `mfa: true` |
| POST | `/auth/mfa/setup` | authenticated, platform admin not yet enrolled → `{secret, otpauthUrl}` |
| POST | `/auth/mfa/enable` | authenticated. body `{code}` confirms enrolment → a new two-factor session (every other session of the admin is revoked) |
| POST | `/auth/google` | *public*, rate limited like login. body `{credential}` (Google ID token) → a session, **or** `{signupRequired: true, invited, email, name}` (no ElProof login for this Google account — continue at `/public/signup/workspace`), **or** `{linkRequired: true, email, name}` (a staff login with this email exists — confirm its password at `/auth/google/link`) (ADR-0024) |
| POST | `/auth/google/link` | *public*, rate limited. body `{credential, password}` — connects the Google account to the existing staff login with the same email → a session |
| GET | `/auth/links/{token}` | *public*, rate limited (60 / 15 min / IP), `Cache-Control: no-store`. What a one-time invitation / reset link is for: `{purpose, tenantName, displayName, username?, email?, expiresAt}`; unknown, used or expired token → 404 `errors.code = link_invalid` (ADR-0025) |
| POST | `/auth/links/{token}/google` | *public*. Staff accepts an invitation with Google: body `{credential}` → a session |
| POST | `/auth/links/{token}/password` | *public*. A client sets their own password: body `{password}` → a session |
| GET | `/public/config` | *public* — `{googleClientId}`, the non-secret setting the web needs before sign-in |
| GET | `/health` | *public* — `{success: true, message: "ok", data: null}` |

## `access` (workspace roles and permissions — Pengaturan → Peran & Akses) — **implemented, ADR-0026**

A workspace's roles decide what its staff and its clients may do; every other module's gate is a permission key of the caller's role (the catalog below). Staff routes need a staff principal; `GET /access/me` is also open to a client (the portal shows only what its portal role allows).

| Method | Path | Notes |
|---|---|---|
| GET | `/access/me` | staff **and** client — the caller's own grants: `{roleId, roleName, isOwner, projectScope: "all"\|"assigned", permissions: [key, ...]}` (catalog order). 403 for an account with no workspace role |
| GET | `/access/catalog` | any staff role — every permission with its plain-language description, grouped for the matrix: `[{key, kind: "staff"\|"client", group, label, description}]` |
| GET | `/access/roles` | needs `role.manage`, `team.manage` or `client.manage` (the role pickers of the team and client forms read it). `?kind=staff\|client` filters. Not paginated. Item `{id, kind, name, description, templateKey?, isSystem, projectScope: "all"\|"assigned", permissions: [key, ...], memberCount}` |
| POST | `/access/roles` | needs `role.manage`. body `{kind, name, description, projectScope, permissions}` → 201 the role. 422 per field, all at once: `name` (2–60 characters, not "Owner", unique in the workspace), `description` (≤ 255), `kind` (`staff`\|`client`), `projectScope` (staff roles only: `all`\|`assigned`; a client role is always `all`), `permissions` (a key the catalog does not know for that kind); a role may not grant a permission the caller does not hold themself (403, "Minta Owner untuk mengaturnya") |
| GET | `/access/roles/{id}` | same gate as the list → the role |
| PATCH | `/access/roles/{id}` | needs `role.manage`; body as `POST`. 403 when it is the Owner role, or — for a caller who is not the Owner — the role the caller holds themself (they could otherwise grant themselves anything), or a permission beyond the caller's own. → the role |
| DELETE | `/access/roles/{id}` | needs `role.manage`. 403 for a built-in (`isSystem`) role or the caller's own role; **409** while people still hold the role ("Peran ini masih dipakai N orang"). Hard delete |

## `payment` — "one merchant wallet, many consumers" — **implemented, internal + external mode (Fase 9 + Fase 10)** — see [`knowledge/MODULE_PAYMENT.md`](../knowledge/MODULE_PAYMENT.md)

| Method | Path | Notes |
|---|---|---|
| POST | `/webhooks/payment` | **Path has no `/api/v1` prefix.** **Unauthenticated** (no JWT — the gateway can't carry a bearer token). Trust comes entirely from `X-Callback-Signature` (HMAC-SHA256 of the raw body, keyed with the merchant private key), verified inside the handler. Idempotent — a duplicate delivery of the same event is a no-op. The single, permanent callback URL registered with Tripay; never changes as new Apps are added. Dispatches to `kind=internal` Apps in-process, or relays (HMAC-signed, fire-and-forget) to `kind=external` Apps' `callback_url`. A charge whose webhook never arrives at all is still eventually resolved by a periodic reconciliation sweep (`PAYMENT_RECONCILE_INTERVAL`, default 3m) that re-checks the gateway directly — see `knowledge/MODULE_PAYMENT.md` §6 step 6. |
| GET | `/payment/gateway-config` | `platform_admin` only (every platform role may read). Returns `{activeProvider, isSandbox, tripayMerchantCode, hasTripayApiKey, hasTripayPrivateKey}` — booleans only for the two secret fields, never the plaintext/encrypted value itself. |
| PATCH | `/payment/gateway-config` | Super Admin only. Body `{activeProvider, isSandbox, tripayMerchantCode, tripayApiKey, tripayPrivateKey}` — `tripayApiKey`/`tripayPrivateKey` are write-only: an empty string means "leave the currently-stored value unchanged," never "clear it." |
| GET | `/payment/apps` | `platform_admin` only. Lists every App (internal + external) — `{appId, name, kind, callbackUrl, isActive, createdAt}`, never the secret hash/encrypted copy. |
| POST | `/payment/apps` | Super Admin only. Body `{name, callbackUrl}` → registers a new `kind=external` App, returns `{appId, name, secret}` — the plaintext secret is shown exactly once. |
| POST | `/payment/apps/{appId}/reset-secret` | Super Admin only. Rotates an external App's secret, returns `{appId, secret}` — again, shown once. |
| POST | `/payment/apps/{appId}/toggle-active` | Super Admin only. Single toggle (flips current state; one of the Platform Console toggles that stay); rejected for `kind=internal` Apps — disabling `platform-billing` would sever ElProof's own subscription billing. |
| POST | `/auth/app/token` | **Unauthenticated** (this IS the login step for external Apps) but rate-limited per IP. Body `{appId, secret}` → `{accessToken, tokenType: "Bearer", expiresIn}`. No refresh token — the App re-exchanges appId+secret once expired. |
| POST | `/external/payments/charges` | `app` principal only (see below). Body `{orderRef, amount, channel?, customerName?, customerEmail?, customerPhone?}` — `appId` always resolved from the token, never the body. Duplicate `orderRef` → `409` with `errors.code = "conflict"`. |
| GET | `/external/payments/charges/{orderRef}/status` | `app` principal only. `404` if `orderRef` doesn't belong to the calling App. |
| GET | `/external/payments/channels` | `app` principal only. |

**The `app` principal (Fase 10):** minted only via `/auth/app/token`, never through `/auth/login`.
Every `/external/payments/*` request re-checks the App's `is_active` status live against the
registry (not just JWT validity) — deactivating an App from Platform Console's "Manajemen Aplikasi"
page takes effect on the very next request, not at token expiry. The three external routes return
an additional machine-readable `errors.code` (`bad_request`/`unauthorized`/`forbidden`/`not_found`/
`conflict`/`rate_limited`/`internal`) alongside the usual `message` — every other route in the app
is unaffected, this is additive.

### Platform Console back office (Fase 6, ADR-0030)

All timestamps in these responses carry the WIB offset (+07:00). Changing a tenant's `email` through `PATCH /tenants/{id}` is Super Admin only (403 `forbidden_role` for Support). Role policy (`cmd/server/platform_scope.go`, enforced for every module's routes once): every platform role may read except **Read-only**, which cannot read
a workspace's internals (`/console/tenants/**`, `/console/data-requests`, `/console/support-sessions`,
`/tenants/export`). Writes: **Billing** — plans (each with its owning App, ADR-0040), `/trial-limits` and `/tenants/{id}/activate-subscription`; **Support** — registering/editing a tenant and its logo, `owner-invite`, notes, data requests, starting/ending a support session; **Super Admin** — everything, and alone: announcements, subscription policy, audit log, login photos, freezing/suspending tenants, platform admins, the payment gateway and external Apps; **Read-only** — nothing. A route that is not classified is Super Admin only (deny by default).

| Method | Path | Notes |
|---|---|---|

### Tahap 4 (E3, E7, E10) — signed uploads, a payment recorded with its proof, `Idempotency-Key`, a project created whole (ADR-0033)

All additive: the base64 `POST /projects/{id}/evidence` and the old two-call flow keep working unchanged.

**`POST /projects/{id}/uploads`** — staff; needs `project.edit` **or** `finance.record` (the same as the evidence upload; a `client` principal gets 403, another workspace's staff 404). Body `{fileName, mimeType, size}`. `fileName` ≤ 150 characters with no `/`, `\` or control character; `mimeType` one of `image/jpeg`, `image/png`, `image/webp`, `image/heic`, `image/heif`, `application/pdf`; `size` 1 … 15 MiB (15 728 640). **201** `data`:

```json
{ "uploadToken": "<payload>.<signature>", "method": "PUT", "url": "https://… or /api/v1/projects/{id}/uploads/{uploadToken}",
  "headers": { "Content-Type": "application/pdf" }, "expiresAt": "2026-11-09T21:15:00+07:00", "direct": true }
```

The browser sends the file with `method` to `url` with `headers` (one code path): `direct: true` means `url` is a presigned URL of object storage itself (storage reachable from browsers, `S3_PRESIGN`), `direct: false` means it is this API's own route below. The token is stateless and HMAC-signed (key derived from the JWT secret with a purpose label); it carries workspace, project, object key, declared type, file name, size cap, expiry (15 minutes) and a random nonce. Nothing is stored when it is granted. 422 per field (`fileName`, `mimeType`, `size`), all at once.

**`PUT /projects/{id}/uploads/{uploadToken}`** — the raw bytes (no JSON), same staff authorization. `Content-Type` must equal the declared type (422 `contentType`), the body may not exceed the declared size (413 `size`; never above 15 MiB) nor be empty (422 `size`); a token that is malformed, expired, tampered or for another workspace/project is 422 `uploadToken`. JPEG/PNG go through the usual server-side re-compression. A retried PUT before a payment used the token is fine; once an evidence row owns the object the token is spent and a PUT answers **409** `upload_token_used` (a recorded proof cannot be overwritten). **200** `data: {size}`.

**Payment create — `POST /projects/{id}/client-payments`, `/payments` (vendor), `/venue-payments`.** The existing body plus an optional `evidence: [{uploadToken, type, name?}]` — at most 4 items; `type` is `"Transfer Proof"` for a client payment and `"Invoice"` and/or `"Transfer Proof"` for vendor and venue payments; `name` defaults to `Bukti Transfer - <referenceNumber>` / `Invoice - <referenceNumber>`. Uploads are verified first (token valid and for this workspace + project, not already used, object present in storage, within its size cap and of the declared type — an object that is present but wrong is deleted); then **one database transaction** locks the project row, applies the overpayment rule, inserts the payment and one `evidence` row per file (`relatedKind` = the new payment, `documentDate` = `paymentDate`, uploaded by the caller, `isClientVisible` false), writes the same activity entries as the two-call flow and computes the ledger from the rows just written. Any failure rolls everything back: there is never a payment without the proof it was recorded with, and nothing partial is visible. A token can prove only one payment (unique index on `evidence.storage_path`); two requests racing with one token create exactly one payment. Objects uploaded but never committed are left in storage (see ADR-0033). **201** `data` = the payment object exactly as the list returns it (`evidence: [{id, type, fileName, uploadedAt}]` is now on vendor and venue payments too, in lists as well; `evidenceComplete` is true at once when the proof is complete) plus `ledgerSummary`:

```json
// client payment
{ "id": 12, "type": "DP", "amount": 15000000, "paymentDate": "2026-11-08", "method": "Transfer", "referenceNumber": "REF-1", "notes": "",
  "evidenceComplete": true, "recordedBy": {"name": "Ani"}, "verifiedAt": null, "verifiedBy": null,
  "evidence": [{"id": 7, "type": "Transfer Proof", "fileName": "bukti.pdf", "uploadedAt": "2026-11-09T14:02:11+07:00"}],
  "ledgerSummary": { "contractValue": 60000000, "paid": 15000000, "remaining": 45000000,
    "terms": [{"id": 3, "label": "DP", "amount": 30000000, "dueDate": "2026-11-14", "paid": 15000000, "remaining": 15000000, "status": "partial"}] } }
// vendor payment: the usual paymentResponse (+ evidence) and  "ledgerSummary": {"contractValue": 5000000, "paid": 2000000, "remaining": 3000000}   // that engagement
// venue payment:  the usual venuePaymentResponse (+ evidence) and "ledgerSummary": {"contractValue": 10500000, "paid": 4000000, "remaining": 6500000} // rental price + charge
```

`ledgerSummary.paid` is what counts toward the contract (DP + Termin + Pelunasan − Refund; `Tambahan` is outside it; never negative), `remaining` is never negative, `terms` is the server's own allocation (the same objects `GET /payment-terms` returns, as of today in Asia/Jakarta). Errors are **422** with one key per problem, all at once: `type`, `amount` (with `errors.code = "payment_exceeds_contract"` for an overpayment, as before), and per evidence item `evidence[i]` **and** `evidence[i].uploadToken` (same message: invalid/expired/foreign/never-uploaded/too-large/wrong-type/already-used token), `evidence[i].type` (type not accepted here) and `evidence[i].name`; `evidence` for more than 4 items. The token problems of items that are fine do not appear. An overpayment keeps the uploads usable: fix the amount and resend the same tokens.

**`Idempotency-Key` header** — on the three payment POSTs above and on `POST /projects`. 8–128 characters of `[A-Za-z0-9_-]` (otherwise **422** `errors["Idempotency-Key"]`); without the header nothing changes. Scoped to the workspace and to method + path (so project and call). First time: the request runs, a 2xx answer is stored for 24 hours and returned; any other answer releases the key (the corrected retry with the same key is a new attempt). Same key + same body (JSON key order and whitespace do not matter) and the first request succeeded: the stored status and body are replayed with header `Idempotent-Replay: true` and nothing is created. Same key + a different body (or another person): **422** `{errors: {"Idempotency-Key": ["…"], "code": "idempotency_key_reuse"}}`. Same key while the first request is still running: **409** `{errors: {"code": "idempotency_in_progress"}}`. Table `idempotency_keys` (DB_SCHEMA.md).

**`POST /projects` — E7 additions.** Optional body fields: `venueId` (a positive id of this workspace's venue; omitted or `0` = no venue), `venueRentalPrice`, `venueCharge` (each 0 … 10^15; **omitted = the venue's current price** — the project's own snapshot, as the web did), `terms: [{label, amount, dueDate}]` (the same rules as `PUT /payment-terms`: ≤ 20, label ≤ 100 characters, amount 1 … 10^15, `YYYY-MM-DD`, together not above `contractValue` when one is set). In **one transaction** the server creates the project, its default milestones, attaches the venue (the project's `venue` text becomes the venue's name, as when attaching later) and saves the schedule; it validates everything first and answers **one 422** with every problem of every part — keys `eventDate`, `prepStartDate`, `picStaffId`, `venueId` ("Venue tidak ditemukan", also for another workspace's venue), `venueRentalPrice`, `venueCharge`, `terms` (count / sum above contract), `terms[i].label|amount|dueDate` — and creates nothing. Trial quota and permissions are unchanged (403 `trial_limit_reached` is answered after validation). **201** `data` = the project exactly as before (`venue` stays the text) plus `terms: [{id, label, amount, dueDate, paid, remaining, status}]` (`[]` when none were sent) and `venueSummary: {id, name, address, city, capacity, facilities, socialMedia, hasVisibleAttachment} | null` (the same shape as `GET /projects/{id}/venue`; its own key because `venue` is already the project's text).

**E10 on these routes:** every validation answer here is a 422 `{success:false, message, errors:{<field>: [messages]}}` (plus `errors.code` where a stable reason exists); `message` is the first problem, followed by "Ada N isian lain yang perlu diperbaiki." when there are more.

```json
}
```
`cashFlow` has exactly 8 entries, the first being the week (Monday–Sunday) that contains today; `weekStart` is that Monday. `expectedIn` = what the clients still owe on payment-schedule installments due that week (each project's real payments allocated over its schedule, oldest first); `expectedOut` = what is still owed on non-cancelled vendor engagements with a due date (`contractValue − DP − Termin − Pelunasan + Refund`, never negative) by due date; anything already overdue counts in week 1, anything beyond week 8 is left out. `vendorPaymentsDue` — those same unpaid vendor balances that are overdue or due within 30 days, nearest first, at most 10. `unconfirmedVendors` — engagements still `Planned`/`Negotiation` whose event is 0–30 days away, soonest event first, at most 10. **`cashFlow` and `vendorPaymentsDue` need `dashboard.revenue.view`: without it the keys are absent and nothing money-related is computed; `unconfirmedVendors` is always present.**

### Tahap 6 (E11, E13 bulk, E14) — sorting, filters, derived columns, bulk activate/deactivate (ADR-0035)

All additive: with none of the new parameters every list answers in the order it had (`ORDER BY id` lists now read `createdAt:asc`, the same
order), and `?all=true` and the older shapes are untouched.

**`?sort=field:asc|desc`** on every paginated list below. One column; `field` alone means ascending; the direction word is case-insensitive, the
field name exact. The field must be in the endpoint's whitelist (table below) or the answer is **422** with a single message under `errors.sort`:

```json
{ "success": false, "message": "Parameter urutan tidak valid",
  "errors": { "sort": ["Urutkan menurut salah satu dari: contractValue, createdAt, eventDate, name, nextDueDate, remaining, status"] } }
```

A bad direction (`name:up`) answers `"Arah urutan harus asc atau desc"`; two `sort` parameters, a comma list, `field:asc;DROP …`, a backquoted name,
`1` … are all just "not in the whitelist" (nothing of the value reaches the SQL). The primary key is always the last sort key, in the same direction,
so equal values page in a stable order. A column that may be empty (`priceAkad`, `city`, `nextDueDate`, `trialEndsAt` …) puts its empty values **last in
both directions**. The effective sort is echoed in `meta.sort`; the three other keys are unchanged:

```json
{ "success": true, "message": "ok", "data": [ … ],
  "meta": { "page": 1, "limit": 10, "total": 37, "total_pages": 4, "sort": "remaining:desc" } }
```

**`q`** is the common name of the free-text search; `search` (what every list accepted first) stays and means the same; `q` wins when both are sent.
Boolean filters (`isActive`) take exactly `true` or `false` (422 under their key otherwise); dates are `YYYY-MM-DD` (422 under their key otherwise).

### Tahap 8 (E9) — partial PATCH, optimistic concurrency with `If-Match`, explicit state instead of toggles (ADR-0036; `If-Match` made required in Tahap 9)

**Partial PATCH.** The body is a JSON object; only the keys present change. A key that is absent keeps its value; a key that is present is validated as on create, with the same 422 `errors` keyed by field (several problems together). `null` clears a field **only** where the table below says nullable; `null` on any other key is 422 `errors.<key>: ["Wajib diisi"]`. A body with no recognised key (`{}`, or only unknown keys) is 422 `errors.body`; a body that is not valid JSON or not an object is 400. A wrongly typed or badly formatted value is 422 on its own key (dates `YYYY-MM-DD`, message "Gunakan format YYYY-MM-DD"). Rules that look at several fields (a milestone's dates, a payment's amount against the contract, an issue's vendor and vendor milestone) are judged on the **merged** result. Only the columns that really changed are written, so two people editing *different* fields of one item without a version both land. A patch that changes nothing writes nothing, logs nothing and answers 200 with the unchanged item (even with a stale `If-Match`: nothing can be lost). One activity entry per effective patch names only the changed fields, in Indonesian ("Informasi project diperbarui: nama, tanggal acara").

**Versions.** An item's version is its `updatedAt` (RFC 3339, six fractional digits, UTC); the same value is the `ETag: "<updatedAt>"` header of every single-item answer (`GET /projects/{id}`, creates, PATCH answers) and a PATCH sends it back as `If-Match` (quotes optional; `W/…`, `*`, lists and anything that is not one RFC 3339 timestamp are malformed → 400 `errors["If-Match"]`). List items carry `updatedAt` but no `ETag` header; `GET /projects/{id}/overview` carries it as `data.project.updatedAt`. Any write to a row bumps its version, including non-PATCH changes (reordering milestones, cancelling or deleting an engagement, verifying a client payment, a project status transition), so a held version goes stale — by design. The write is a compare-and-set in the same SQL statement (`… WHERE id = ? AND updated_at = ?`), never read-then-write.

**`If-Match` is required — 428 `Precondition Required` — on a field edit.** Without the header: nothing is written and the body is not judged, `errors: {"If-Match": ["wajib"]}`, message "Sertakan versi data (If-Match) agar perubahan tidak menimpa orang lain. Muat ulang data lalu coba lagi." The order of answers is: malformed header 400 → (for milestones, vendors, vendor milestones, kendala and payments) a row that does not exist or is another workspace's is the usual 404, so a 428 never tells the two apart → missing header 428 → body judged (400/422) → stale version 409. For `PATCH /projects/{id}` the body must be a JSON object (400) before the header is looked at.

| Resource | `If-Match` |
|---|---|
| Project (`PATCH /projects/{id}`), project milestone, project vendor, vendor milestone, kendala, client payment, vendor payment, venue payment | **required (428)** |
| Project `PATCH` whose body is **exactly** `{"isArchived": bool}` | optional — honoured when sent |
| Evidence `PATCH {"isClientVisible": bool}` | optional — honoured when sent |
| The five directory state changes `PATCH {"isActive": bool}` on vendor, venue, vendor category, client, staff | not read: the header is ignored (these rows have no version) |
| `PATCH /projects/{id}/milestones` (reorder), `PUT /projects/{id}/payment-terms`, `cancel`, `transition`, `verify`, `restore`, `DELETE` | not applicable |

A project body that mixes `isArchived` with other keys is a field edit and needs the header.

**409 `Conflict` (stale).** The row exists but is at another version than the one sent:

```json
{ "success": false,
  "message": "Data ini sudah diubah orang lain. Muat ulang untuk melihat versi terbaru.",
  "errors": { "_conflict": ["stale"] },
  "data": { "current": { "…": "the item as it is now, same shape as the 200 answer's item, incl. updatedAt" } } }
```

No `ETag` header on a 409. With `If-Match`, a change that would be judged on a row that has already moved past the version sent is answered 409 *before* any rule runs (so the caller never gets a 422 about data it has not seen). Soft-deleted rows are 404 for PATCH (restore is its own call).

**Success `200`:** `{ success, message, data: <the item, as the list shows it, with its new updatedAt> }` and header `ETag: "<updatedAt>"`. Most answers go through the mutation envelope of *Tahap 5*, so `data` also carries `projectProgress` (and `ledgerSummary` on payments); the project `PATCH` answer is the project itself (as `GET /projects/{id}`) without `projectProgress`.

## Client Portal (read-scoped subset — same `projects` endpoints, `client` principal) — **implemented, Fase 6**

`client` principals hit the same `/projects/{id}/...` GET endpoints as staff, on a **fixed allowlist** (`cmd/server/client_scope.go`, checked before any
handler, deny by default): `auth/me`, `access/me`, `tenants/me/branding|logo|contact`, `projects/me`, `projects/me/home`, `projects/{id}` and, under it, only
`milestones` (`portal.timeline.view`), `vendors` and `venue` (`portal.vendor.view`), `client-payments` and `payment-terms` (`portal.finance.view`), `issues`
(`portal.issues.view`), `evidence` (list: `portal.documents.view`) and `documents` (`portal.documents.view`), `evidence/{id}/file|link` (judged per file, see
`link` above), plus `venues/{id}/attachment`. **Not reachable by a client** (403): `payments`, `venue-payments`, `activity`, `overview`, `closing-checklist`,
`vendors/{id}/milestones`, `uploads`, every other module, and any non-GET method. The Pembayaran tab reads `client-payments` (the client's own payment history),
never `payments`/`venue-payments` (the WO's spend on vendors/venue) — "Uang Masuk dari Client" is a distinct concept from money spent on vendors/venue. The Client Portal's own
"Dokumen" tab (appended after Kendala, ADR-0020) reads `GET .../documents` specifically — never `GET .../evidence` directly, which stays unfiltered by kind and would leak every
other evidence kind if it were not filtered per file (see `DB_SCHEMA.md`'s `evidence.is_client_visible` note). The one route outside `/projects/{id}/...` is `venues/{id}/attachment`,
a `venues`-module route that `client` principals also reach, gated by mime type (image only) rather than by project ownership, since it isn't itself project-scoped. Enforcement, checked
server-side on every request (not just a frontend routing convention):
- Only `GET` is ever allowed for a `client` principal — any `POST`/`PATCH`/`PUT`/`DELETE` is rejected 403 before reaching any business logic, even for the client's own project.
- `{id}` must equal the one project resolved for that client via `clients.Contracts.ProjectIDForClient` (new in Fase 6) — any other `{id}` (including a real project belonging to a *different* client
  in the same tenant) is rejected 403.
- The client's own project id is learned via `GET /projects/me/home` (`data.project.id`) or `GET /projects/me` — there is no other way, by design (login doesn't return one; `identity` stays
  profile-agnostic per ADR-0005).

A deactivated client (`clients.is_active = false`) is also rejected 403, even for their own project, and a soft-deleted one is locked out at once (ADR-0034).

**Tahap 3 additions (E4, E5, E6 — `docs/plan/revamp-ui-shadcn/PLAN.md`, ADR-0032).** All additive to existing responses except the two closed endpoints:
- `GET /projects/me/home` (above) is the one call behind the portal home.
- Names and proof come inside already-filtered responses so the portal needs no directory calls: `vendorName`/`categoryName` on `GET /projects/{id}/vendors` items, `vendorName`/`vendorMilestoneName` on `GET /projects/{id}/issues` items, `evidence[]` on milestones, vendor milestones, client payments and issues, and `verifiedAt`/`verifiedBy` on client payments.
- **Closed for clients:** `GET /vendor-categories` (any query) answers 403 for a `client` principal; it is not on the allowlist. `GET /vendors/summary` no longer exists (removed in Tahap 9); the path stays off the allowlist, so a client still gets 403 on it and staff get no 200.
- `recordedBy` (who entered a payment) is never sent to a client; `verifiedBy`/`verifiedAt` are. Kendala flagged `isClientVisible = false`, a step's attachment that staff did not flag, and a soft-deleted item never reach a client.
- Verification and the staff-only `POST .../client-payments/{pid}/verify` are described in the `projects` table above.
