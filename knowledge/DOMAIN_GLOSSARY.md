# Domain Glossary

> Shared terminology used across the project.

| Term | Meaning |
|---|---|
| **Tenant** | One WO (Wedding Organizer) business subscribed to ElProof. Owns its own staff, clients, vendors, and projects — never shares data with another tenant. Also carries its own identity — its business name and an optional logo (object storage, ADR-0006) — shown in the WO Console and Client Portal header and the browser tab. There is no per-tenant colour: every surface uses the one ElProof palette (ADR-0039). See `MODULE_PLATFORM.md` §6. |
| **Owner** | The locked system role of a workspace (ADR-0026): created with the tenant, always holds every staff permission, cannot be edited or deleted, and the name "Owner" is reserved. Exactly one Owner login per tenant. Distinct from `platform_admin`. See **RBAC**. |
| **Admin** | A built-in, editable staff role template (ADR-0026): all projects, clients, vendors and finance; no workspace settings (team, roles, subscription, business profile, vendor categories, Timeline Default) and no hard deletes of projects or vendors. See **RBAC**. |
| **Wedding Planner** | A built-in, editable staff role template (ADR-0026; legacy role `"Staff"` was migrated to it). Scope `assigned`: only projects where the person is PIC or PIC Sales; may edit them and record payments. Other templates: **Sales** (assigned; creates projects, manages their clients) and **Keuangan** (all projects; records and monitors payments). See **RBAC**. |
| **RBAC** | Per-workspace roles (ADR-0026, supersedes ADR-0017): a fixed permission catalog in code (22 staff + 7 portal permissions; `package.manage` added by paket WO Tahap 1, `quotation.view` and `quotation.manage` by Tahap 5), roles per tenant in `tenant_roles` that the Owner can edit or create at Pengaturan → Peran & Akses, each with a project scope (`all` / `assigned`). The backend checks `Grants.Can(key)` per request (`middleware.LoadGrants`); the web mirrors it with `useCan` / `RequirePermission`. Client roles (**Pengantin**, **Keluarga**, or custom) decide what the portal shows. |
| **Pengaturan** | The WO Console sidebar's collapsible settings group — `Pengguna`, `Peran & Akses`, `Langganan`, `Kategori Vendor`, `Timeline Default` — collapsed by default. Each entry appears only for roles holding its permission (`team.manage`, `role.manage`, `subscription.manage`, `vendor.category.manage`, `template.manage`); by default only the Owner. Kategori vendor and Jadwal bawaan (Timeline Default) now sit in **Katalog**, not here. |
| **Katalog** | The WO Console sidebar group (paket WO Tahap 1, replaces the former Templat group) holding what every offer and project is built from: **Paket**, **Jenis acara** (`package.manage`), Jadwal bawaan (`template.manage`) and Kategori vendor (`vendor.category.manage`). Viewing packages and event kinds through the API stays open to every staff role, since they are picked in offers. |
| **WO Console** | The tenant-facing app surface (`/dashboard`, `/projects`, `/clients`, `/vendors`, `/vendor-categories`, `/venues`, `/pengguna`, `/langganan`, `/timeline-default`). |
| **Platform Console** | ElProof's own internal admin surface (`/platform/*`), used by ElProof staff (`platform_admin`), never by tenants. |
| **Client Portal** | Mostly read-only surface (`/portal/*`; since ADR-0047 the couple may send a transfer proof and mark their own tasks done) for a wedding's bride/groom/family to track their own project — five tabs (Vendor, Timeline, Pembayaran, Kendala, **Dokumen**, ADR-0020), Dokumen appended last since it's a newer, separate, opt-in capability rather than a reordering. |
| **Principal** | Whoever is authenticated: `staff` (WO Console), `client` (Client Portal), `platform_admin` (Platform Console), or `app` (an external SaaS consumer of `payment`'s Fase 10 API, minted via `POST /auth/app/token` — no `credentials` row, no refresh token). See ADR-0005 and its update. |
| **App** (payment) | A consumer registered in `payment`'s App registry (`payment_apps`), allowed to create charges through ElProof's one gateway wallet. `kind=internal` (in-process, e.g. `platform-billing` — ElProof's own subscription billing) or `kind=external` (HTTP, another SaaS product, managed via Platform Console's "Manajemen Aplikasi"). Not to be confused with the `App` React component or "application" in a general sense — always refers to this registry concept. See `MODULE_PAYMENT.md`. |
| **Konfigurasi Gateway** | Platform Console page (`/platform/pembayaran`) for choosing the active payment provider (Tripay) and its sandbox/production credentials — write-only, never echoes a stored secret back. |
| **Manajemen Aplikasi** | Platform Console page (`/platform/aplikasi`) for registering/managing external Apps (see above) — reveal-once secrets, reset, toggle active/inactive. |
| **Reconciliation sweep** | `payment`'s background safety net (`ReconcilePending`) for a charge whose webhook was never received — periodically re-checks still-open charges directly against the gateway and force-resolves anything left open long past its own expiry. See `MODULE_PAYMENT.md` §6 step 6. |
| **Project** | One wedding engagement managed by a tenant. Has a lifecycle status (`Draft→Preparation→Ready→Completed`/`Cancelled`) that changes only through explicit actions (`/transition`, `/cancel`), never by editing the project — ADR-0027 and owns Timeline items, **Acara** (at least one; one of them the **acara utama**, whose date is the project's `eventDate`, "Hari H"), **Vendor & venue**, payments, issues, evidence, activity. A project has no single venue of its own: each event names its own, so one wedding can use several venues, and the project's location line is derived from its events' venues (paket WO Tahap 2, ADR-0048). Also has an `is_archived` flag, orthogonal to status (reversible, any staff role) — and can be permanently hard-deleted (Owner-only, requires already archived or cancelled first) — see ADR-0013. Can also be **duplicated** into a brand-new project, cloning its Timeline, its events and its vendors & venues (except cancelled ones, each reset to Planned) as a reusable template (payments/issues/evidence/activity/clients are never copied) — see ADR-0014. Only Owner/Admin create or duplicate a Project, or reassign its PIC — see **RBAC** above. |
| **Timeline** (Project Timeline) | The wedding's own top-level checklist — display label only; the underlying identifier, DB table (`project_milestones`), and API shape are still "milestone" everywhere (deliberate, display-text-only rename). Seeded into every new project from that tenant's own **Timeline Default Template**, not a single list shared by every tenant. A seeded step keeps its offset (`daysBeforeEvent`) and its target date follows the event date until someone dates it by hand (ADR-0042). UI words: **Jadwal** (the list), **tahapan** (one step). |
| **Tanggal Booking** | Display label only — the underlying identifier/column/API field is still `prepStartDate`/`prep_start_date` everywhere (deliberate, display-text-only rename, same convention as **Timeline** above). Feeds the dashboard's "Progress Tertinggal" lagging calculation and new-project Timeline seeding exactly as before; only the label changed. |
| **Timeline Default Template** | A tenant's own configurable checklist (name + a signed day-offset per item), managed from Pengaturan → Timeline Default (Owner-only), auto-copied into a new project's own Timeline the moment it's created. Replaces what used to be one hardcoded 6-item list shared by every tenant. An item's offset can be positive ("H-", before the event) or negative ("H+"/"Setelah Acara", after it — e.g. returning the seserahan box a few days post-event); the form presents this as a Sebelum Acara/Setelah Acara toggle, not a signed number field. A newly registered tenant gets the same starter 6 H- items seeded automatically; editing the template afterward never retroactively changes any already-created project's Timeline, and has no effect on Duplikat Project (which clones the *source project's* actual Timeline, not the tenant's current template). |
| **Acara** (Event) | One part of a wedding inside a project (`project_events`, ADR-0048): a **Jenis acara**, a date, optional hours, an optional **Venue**, a **Tata letak** (**Berdiri** / **Duduk**, which of the venue's two capacities applies) and one or more **Sesi**. Exactly one event is the **acara utama**: its date is the project's event date, and moving it moves the H-n steps of the Jadwal with it. A project keeps at least one event; deleting an event is permanent. Events are ordered by date; two on the same date can be swapped. Never "Event" in the UI. |
| **Sesi** (Session) | A time range inside one **Acara** with its own **Tamu** count (`project_event_sessions`); an event that is not split has one session. The event's guests are the sum of its sessions, and each session is checked against the capacity of the event's venue for the event's tata letak. |
| **Vendor & venue** (project supplier) | One vendor or venue taking part in a project (`project_suppliers`, ADR-0048) — not the directory record itself. Keeps a copy of the name, category and, for a venue, the two capacities ("Perbarui kapasitas" refreshes them from the directory), plus scope, status, PIC, booking and due dates, **Dibayar oleh**, whether the client may see its name (otherwise the portal shows its category, or "Layanan"), and the **Biaya rekanan**. A vendor is added on the Vendor & venue tab; a venue only by choosing it for an **Acara**. The UI never says "Pemasok"; the API and code say supplier. |
| **Dibayar oleh** (`paidBy`) | Who pays a **Vendor & venue**: **WO** (part of what the client pays the WO) or **Klien langsung** (the client pays the vendor or venue). Locked once a payment or file is recorded against it; switching to Klien langsung clears the Biaya rekanan and shows the name to the client. Each payment also keeps its own payer, so a later change never rewrites history. |
| **Biaya rekanan** (`agreedCost`) | What the WO has agreed to pay a vendor or venue it pays itself. Optional, never below what the WO has already paid it, and seen or edited only with `finance.margin.view`; empty or 0 does not limit payments. The catalog's equivalent is **Perkiraan biaya**. |
| **Pembayaran ke rekanan** (supplier payment) | A payment to one **Vendor & venue** (`supplier_payments`), by the WO or by the client directly (its payer). The WO's own payments are money out and need `finance.margin.view`; the client's direct payments are shown to the client in the portal. Not to be confused with client payments to the WO ("Uang Masuk dari Client"). |
| **Tagihan vendor** (supplier bill) | One bill of a **Vendor & venue** the client pays directly (**Dibayar oleh** Klien langsung): a label, an amount and a due date (`supplier_bill_terms`, paket WO Tahap 4). The couple pays the vendor and sends **bukti bayar** from the portal (*Pembayaran › Tagihan vendor*, `portal.finance.submit`); the proof is "menunggu diperiksa" and counts as paid only once the WO marks it right (**Sesuai**) — or the WO refuses it with a reason (**Ditolak**). Paid amounts are spread over the bills earliest due date first, like the client's termin. The client's own money: never in the WO's cash, revenue, cash flow or payables, and never part of the **Nilai kontrak**. Keluarga (no `portal.finance.view`) never sees it. A supplier with a live bill cannot switch to WO-paid. |
| **Margin** (Margin/Keuntungan) | A project's contract value minus the **Biaya rekanan** of every live, not cancelled vendor and venue the WO pays (`margin` in `GET /projects/{id}/overview`, with `supplierCost` and `missingCost` — how many of them have no cost yet, "Margin belum lengkap"). A vendor or venue the client pays directly is outside it. Present only for `finance.margin.view`. |
| **Vendor Milestone** (Tahapan vendor) | A checklist item tracked against one **Vendor & venue** of a project (distinct from a Project's own Timeline). `vendor_milestones` table/identifiers unchanged. |
| **Venue** | A bookable wedding location — its own directory (ADR-0016), still inside the `vendors` module but not a vendor category. Carries fields a generic vendor doesn't (two capacities — **Kapasitas berdiri** and **Kapasitas duduk**, at least one required and ≥ 1; three optional prices — **Harga Akad**, **Harga Resepsi**, **Harga Akad + Resepsi**; an optional **Charge tambahan**; facilities; a single document/photo attachment — paket WO Tahap 1, ADR-0048, replaced the single capacity and rental price, in the form, import and export alike) and enters a project only through an **Acara**: choosing it for an event adds it to the project's **Vendor & venue** (one row however many events use it, with its own Dibayar oleh, Biaya rekanan and payments), so a project can use several venues. Commercial fields (prices, charge, PIC contact) are staff-only; Client Portal sees only the public-safe subset with the events. Can also be permanently hard-deleted (Owner-only, informed-consent — ADR-0018), same guardrail model as Vendor/Pengguna — refused while a project uses it or a **Paket** names it as its default venue. |
| **Jenis acara** (Event kind) | One kind of event a WO organises (`offers.event_kinds`, ADR-0049). Every workspace starts with six built-in kinds — Lamaran, Pengajian, Siraman, Akad, Resepsi, Ngunduh mantu — and may add its own, rename any (a renamed built-in kind keeps its `default_key`), or deactivate one so it can no longer be picked. A kind a package covers cannot be deleted. Events in an offer or project copy its name, so a rename never rewrites an earlier document. Managed at Katalog › Jenis acara (`package.manage`). One event (butir) is an **Acara**. |
| **Paket** (Package) | A product the WO offers its clients (`offers.packages`, ADR-0049): a name, a price, the **Jenis acara** it covers (at least one), an optional **Tamu termasuk** with a **Tambahan per … tamu** rule, an optional default **Venue**, and its **Isi paket**. Managed at Katalog › Paket (`package.manage`); every staff role can read and pick it. Never "Paket" alone for an ElProof subscription — that is **Paket langganan** (see **Plan**). An offer or project line keeps a copy of the package's pricing rule, so editing the catalog later never changes it. |
| **Isi paket** (Package component) | One thing a **Paket** contains ("Katering buffet 450 porsi"): a description, optionally a vendor category and a vendor from the directory, and a **Perkiraan biaya** (the WO's own cost estimate) visible and editable only for roles holding `finance.margin.view`. Always paid by the WO as part of the package. At most 50 per package. |
| **Tamu termasuk / Tambahan per … tamu** | A package's guest rule. **Tamu termasuk** (`includedGuests`) is how many guests the price covers (empty = the price does not depend on guests). **Tambahan per … tamu** is the charge above that: every started step of N guests costs a set price — `ceil((guests − included) / N) × price`, on the largest guest total among the events the package covers (500 included, Tambahan per 50 tamu Rp4.000.000, 620 guests → 3 steps → Rp12.000.000; a step of 1 is per pax). With a default venue, Tamu termasuk may not exceed the venue's largest capacity. The form's "Contoh hitung" is priced by the server (`POST /packages/preview`). |
| **Pengaturan penawaran** (Quote settings) | The **Penawaran** section of Profil usaha (`GET/PUT /tenants/me/quote-settings`, `business_profile.manage`): **Kode usaha**, **PKP**, the default validity of a new offer (14 days unless changed, 1–365) and the default terms (Syarat & ketentuan) copied into each new offer — where the WO also writes what an offer does not include. Created for a workspace at sign-up, or on first read for an existing one. |
| **Kode usaha** (Document code) | 2–5 capital letters or digits that start every offer number (`KODE-PNW-YYMMDD-NNN`). Filled from the business name — the initials (Melati Organizer → `MO`, Bunga Wedding Organizer → `BWO`) or the first three letters of a one-word name (Lavanya → `LAV`) — and changeable by the Owner; a change shapes only numbers created afterwards. Not unique across WOs, since a number never leaves its own WO. |
| **PKP** | Pengusaha Kena Pajak: a WO marked PKP (`is_pkp`, default off) adds PPN to its offers — 12% of a DPP of 11/12 of the subtotal, effectively 11%, rounded down to the rupiah (`offers/domain.LineTotals`). UI words: **PKP** / **Bukan PKP**. |
| **Evidence** | An uploaded document/photo attached polymorphically (`relatedKind` + `relatedId`) to a vendor milestone, supplier payment, project supplier, issue, client payment, project milestone, or nothing (**`general`**, ADR-0020, `relatedId` a sentinel `0`). What a client sees is decided per file (`PortalPolicy`): a general document or a Jadwal step's file only when staff flag it (`isClientVisible`, default hidden; general documents fill the Client Portal's **Dokumen** tab); a Tahapan vendor file when the vendor or venue is paid by the client, or when flagged; a supplier payment's file only for a payment by the client; a project supplier's own file never. Deleting a payment cascades to its own evidence rows. |
| **Pembayaran** (payment ledgers) | The two payment tables inside a project — client payments (money in from the client, "Uang Masuk dari Client") and **Pembayaran ke rekanan** (payments to a vendor or venue, by the WO or by the client directly). Each row can be edited (full-field, no role gate) or hard-deleted (**Owner-or-Admin** — see ADR-0019, the only hard-delete in this codebase that isn't Owner-only); deleting cascades to that payment's own **Evidence** rows first. A payment row's attached evidence can be viewed inline from its own tab via "Lihat Bukti," without leaving the tab. |
| **Granted (transaction status)** | A subscription transaction created by Platform Console manual activation — bypasses payment, deliberately excluded from paid-revenue reporting. Distinct from `paid` (real payment). |
| **Rincian** (Project lines) | What the client buys in one project, line by line (`projects.project_lines`, paket WO Tahap 3): **Paket** lines (a copy of the catalog package's rule, with its **Isi paket** as components that carry no price of their own), the computed **Tambahan tamu**, **Item** lines (jumlah × harga satuan, or a **Bonus** at Rp0) and **Potongan** (discount). Its total is the project's **Nilai kontrak**. The client portal shows the names with `portal.vendor.view` and the amounts only with `portal.finance.view` (Keluarga: names only); a component's price and the vendor behind a line never. |
| **Nilai kontrak** (Contract value) | The total of the **Rincian**: subtotal (packages + extra guests + items − discounts, never negative) plus PPN when the project is **PKP** (copied from the workspace when the project was created). Never typed; every money screen (Keuangan, Ringkasan, portal, ekspor) reads the same cached total. |
| **Tambahan tamu** (Extra guests) | The charge a package rule adds when the decisive event (the covered **Acara** with the most guests over its sessions) has more guests than the package includes: ⌈(tamu − tamu termasuk) / per⌉ × harga per langkah. Computed by the server, updated in the same save as a guest change, never edited by hand. |
| **Penawaran** (Quotation) | The price letter a WO sends a couple before there is a project (`offers.quotations`, paket WO Tahap 5, ADR-0050): the same **Acara**, **Vendor & venue** and **Rincian** a project has, plus **Termin** and **Syarat & ketentuan**, a validity date (**Berlaku sampai**, default 14 days) and a PIC. Numbered `KODE-PNW-YYMMDD-NNN` (the workspace's **Kode usaha**, the WIB day, a daily sequence); the number never changes. Statuses: **Draf**, **Diterima**, **Ditolak**, **Digantikan** (stored) and **Kedaluwarsa** (a Draf past its last day, computed). `quotation.view` / `quotation.manage`. Never "Quotation" or "Proposal" in the UI. |
| **Revisi** (Quotation revision) | A frozen copy of a **Penawaran** as it was sent (`quotation_revisions`): content, letterhead and validity in one JSON snapshot whose PDF is rendered again from it, unchanged, every time. Made by "Buat revisi"; the same content never makes a second revision (content hash). A quotation is accepted on one revision, which must equal the working copy. "Bandingkan revisi" shows what changed between two revisions or a revision and the unsaved edits. |
| **Alternatif** (Quotation alternative) | Another **Penawaran** offered side by side in the same group (e.g. Gold vs Silver). Accepting one makes the group's other Draf **Digantikan**; a **Ditolak** one stays as it is. **Salin jadi baru** is different: a new quotation with a new number that replaces the original. |
| **Jadikan proyek** | Turning an accepted **Penawaran** into a project (PLAN §5.4, owned by `projects`): the project copies the accepted revision through `offers/contracts.Quotations`, keeps it as "Kesepakatan awal", and the quotation becomes read-only. |
| **Hitung ulang termin** (Recalculate terms) | The explicit action (`POST /projects/{id}/payment-terms/recalculate`, `finance.record`) offered when the payment schedule no longer adds up to the **Nilai kontrak** (`termsMismatch`): unpaid installments share what is left in proportion; never done silently. |
| **Margin belum lengkap** | The margin (subtotal − biaya rekanan of the WO-paid vendors and venues, `finance.margin.view` only) when some WO-paid supplier has no biaya rekanan yet: shown with the count ("Margin belum lengkap (n vendor)"). The same suppliers appear in Pembayaran keluar as **Belum lengkap** (`status: incomplete`) instead of being left out. |
| **Plan (Subscription Plan)** | A row in the shared plan catalog (`billing` module) — name, duration, price, feature list. Single source of truth rendered identically on the WO Console's `Langganan` card and the Platform Console's `Paket` CRUD. |
| **Voucher** | A discount code for a subscription payment (`billing`, ADR-0041): percent (1–99, optional cap) or a fixed amount, for one App and optionally one of its plans, with an optional validity period, total quota and once-per-customer rule. UI words: **Voucher**, **Potongan** (discount), **Harga awal** / **Harga akhir** (before / after). A **use** (Pemakaian) is reserved while its charge is pending, used once paid, released if the charge fails. The final price is never Rp0. |
