# Domain Glossary

> Shared terminology used across the project.

| Term | Meaning |
|---|---|
| **Tenant** | One WO (Wedding Organizer) business subscribed to ElProof. Owns its own staff, clients, vendors, and projects — never shares data with another tenant. Also carries its own visual identity — an optional logo (object storage, ADR-0006) and one of 20 fixed brand-color presets (`navy` by default) — applied at runtime across WO Console and Client Portal so a tenant's own staff/clients see that tenant's brand, not ElProof's. See `MODULE_PLATFORM.md` §6. |
| **Owner** | The tenant-side role created by the Platform Console at tenant registration time. Exactly one per tenant conceptually; only the Owner can access `Langganan` (subscription management), `Pengguna`, `Kategori Vendor`, and `Timeline Default` — the whole `Pengaturan` group. The Owner can edit their own name/title/contact details from `Pengguna` afterward — no other staff member (even Admin) can edit the Owner's row, and the Owner's role/username can't be reassigned from there. Distinct from `platform_admin`. See **RBAC** below and ADR-0017. |
| **Admin** | A tenant-side staff role with full access to everything an Owner can reach **except** the `Pengaturan` group (`Pengguna`, `Langganan`, `Kategori Vendor`, `Timeline Default`) — sees and can act on Dashboard, Client, Vendor, Venue, and every Project the same as Owner. See **RBAC** below and ADR-0017. |
| **Wedding Planner** | The user-facing label for the `"Staff"` backend role/enum value (unchanged identifier — display-text-only; see PLAN.md's Milestone→Timeline precedent for why the string itself wasn't renamed). Scoped to only the Projects where they're PIC (`picStaffId`) — cannot see Dashboard, Client, Vendor, Venue, or any `Pengaturan` page at all, cannot create or duplicate a Project, and cannot reassign a Project's PIC (Owner/Admin only). See **RBAC** below and ADR-0017. |
| **RBAC** | The three-role access model above (Owner / Admin / Wedding Planner), enforced on both sides of the stack: backend route guards (`claims.HasRole(...)`, `resolveProjectAccess`'s PIC check) and frontend `Sidebar`/`RequireRole` gating kept 1:1 with each other. Full rule set and rationale: ADR-0017. |
| **Pengaturan** | The WO Console sidebar's collapsible settings group — `Pengguna`, `Langganan`, `Kategori Vendor`, `Timeline Default` — collapsed by default, Owner-only end to end (invisible to Admin and Wedding Planner, not just access-restricted). |
| **WO Console** | The tenant-facing app surface (`/dashboard`, `/projects`, `/clients`, `/vendors`, `/vendor-categories`, `/venues`, `/pengguna`, `/langganan`, `/timeline-default`). |
| **Platform Console** | ElProof's own internal admin surface (`/platform/*`), used by ElProof staff (`platform_admin`), never by tenants. |
| **Client Portal** | Read-only surface (`/portal/*`) for a wedding's bride/groom/family to track their own project. |
| **Principal** | Whoever is authenticated: `staff` (WO Console), `client` (Client Portal), `platform_admin` (Platform Console), or `app` (an external SaaS consumer of `payment`'s Fase 10 API, minted via `POST /auth/app/token` — no `credentials` row, no refresh token). See ADR-0005 and its update. |
| **App** (payment) | A consumer registered in `payment`'s App registry (`payment_apps`), allowed to create charges through ElProof's one gateway wallet. `kind=internal` (in-process, e.g. `platform-billing` — ElProof's own subscription billing) or `kind=external` (HTTP, another SaaS product, managed via Platform Console's "Manajemen Aplikasi"). Not to be confused with the `App` React component or "application" in a general sense — always refers to this registry concept. See `MODULE_PAYMENT.md`. |
| **Konfigurasi Gateway** | Platform Console page (`/platform/pembayaran`) for choosing the active payment provider (Tripay) and its sandbox/production credentials — write-only, never echoes a stored secret back. |
| **Manajemen Aplikasi** | Platform Console page (`/platform/aplikasi`) for registering/managing external Apps (see above) — reveal-once secrets, reset, toggle active/inactive. |
| **Reconciliation sweep** | `payment`'s background safety net (`ReconcilePending`) for a charge whose webhook was never received — periodically re-checks still-open charges directly against the gateway and force-resolves anything left open long past its own expiry. See `MODULE_PAYMENT.md` §6 step 6. |
| **Project** | One wedding engagement managed by a tenant. Has a lifecycle status (`Draft→Preparation→Ready→Completed`/`Cancelled`) and owns Timeline items, vendor engagements, payments, issues, evidence, activity — plus at most one attached **Venue** (`venue_id`, ADR-0016). Also has an `is_archived` flag, orthogonal to status (reversible, any staff role) — and can be permanently hard-deleted (Owner-only, requires already archived or cancelled first) — see ADR-0013. Can also be **duplicated** into a brand-new project, cloning its Timeline and vendor lineup (with each vendor's pricing tier) as a reusable template (payments/issues/evidence/activity/clients are never copied) — see ADR-0014. Only Owner/Admin create or duplicate a Project, or reassign its PIC — see **RBAC** above. |
| **Timeline** (Project Timeline) | The wedding's own top-level checklist — display label only; the underlying identifier, DB table (`project_milestones`), and API shape are still "milestone" everywhere (deliberate, display-text-only rename — see PLAN.md). Seeded into every new project from that tenant's own **Timeline Default Template**, not a single list shared by every tenant. |
| **Timeline Default Template** | A tenant's own configurable checklist (name + days-before-event per item), managed from Pengaturan → Timeline Default (Owner-only), auto-copied into a new project's own Timeline the moment it's created. Replaces what used to be one hardcoded 6-item list shared by every tenant. A newly registered tenant gets the same starter 6 items seeded automatically; editing the template afterward never retroactively changes any already-created project's Timeline, and has no effect on Duplikat Project (which clones the *source project's* actual Timeline, not the tenant's current template). |
| **Project Vendor** | The engagement between a Project and a Vendor (scope, contract value, DP/paid amounts, status, pricing tier) — not the Vendor record itself. |
| **Pricing Tier** (`pricingTier`) | Which of a Vendor's own two preset prices (`priceAkad`/`priceAkadResepsi`) a Project Vendor engagement's contract value was auto-filled from when created/edited — "Akad Saja" or "Akad + Resepsi," picked per engagement (not once for the whole project, since different vendors on the same project can legitimately have different scopes). Purely a stored label: the engagement's own contract value stays freely negotiable and is never re-derived from it afterward. |
| **Margin** (Margin/Keuntungan) | A project's contract value minus every cost sourced for it — the sum of every non-Cancelled Project Vendor's contract value, minus the attached Venue's rental price + charge (0 if none attached). Computed client-side on the fly, never stored. Shown only to Owner/Admin on the Project header — hidden from Wedding Planner, since it reveals vendor/venue cost data that role isn't otherwise allowed to see. |
| **Vendor Milestone** (Timeline Vendor) | A checklist item tracked against one Project Vendor engagement (distinct from a Project's own Timeline). Same display-text-only rename as Timeline above — `vendor_milestones` table/identifiers unchanged. |
| **Venue** | A bookable wedding location — its own directory (ADR-0016), still inside the `vendors` module but not a vendor category. Carries fields a generic vendor doesn't (mandatory rental price, a separate charge, capacity, facilities, a single document/photo attachment) and attaches to a Project 1:1 (`projects.venue_id`), never through a `project_vendors`-style engagement — no per-project negotiated price/DP/paid-amount tracking for it. Commercial fields (rental price, charge, PIC contact) are staff-only; Client Portal's own Venue tab sees only the public-safe subset. |
| **Evidence** | An uploaded document/photo attached polymorphically to a vendor milestone, payment, or issue (`relatedKind` + `relatedId`). |
| **Granted (transaction status)** | A subscription transaction created by Platform Console manual activation — bypasses payment, deliberately excluded from paid-revenue reporting. Distinct from `paid` (real payment). |
| **Plan (Subscription Plan)** | A row in the shared plan catalog (`billing` module) — name, duration, price, feature list. Single source of truth rendered identically on the WO Console's `Langganan` card and the Platform Console's `Paket` CRUD. |
