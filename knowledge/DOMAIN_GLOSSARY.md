# Domain Glossary

> Shared terminology used across the project.

| Term | Meaning |
|---|---|
| **Tenant** | One WO (Wedding Organizer) business subscribed to ElProof. Owns its own staff, clients, vendors, and projects — never shares data with another tenant. Also carries its own visual identity — an optional logo (object storage, ADR-0006) and one of 20 fixed brand-color presets (`navy` by default) — applied at runtime across WO Console and Client Portal so a tenant's own staff/clients see that tenant's brand, not ElProof's. See `MODULE_PLATFORM.md` §6. |
| **Owner** | The locked system role of a workspace (ADR-0026): created with the tenant, always holds every staff permission, cannot be edited or deleted, and the name "Owner" is reserved. Exactly one Owner login per tenant. Distinct from `platform_admin`. See **RBAC**. |
| **Admin** | A built-in, editable staff role template (ADR-0026): all projects, clients, vendors and finance; no workspace settings (team, roles, subscription, business profile, vendor categories, Timeline Default) and no hard deletes of projects or vendors. See **RBAC**. |
| **Wedding Planner** | A built-in, editable staff role template (ADR-0026; legacy role `"Staff"` was migrated to it). Scope `assigned`: only projects where the person is PIC or PIC Sales; may edit them and record payments. Other templates: **Sales** (assigned; creates projects, manages their clients) and **Keuangan** (all projects; records and monitors payments). See **RBAC**. |
| **RBAC** | Per-workspace roles (ADR-0026, supersedes ADR-0017): a fixed permission catalog in code (21 staff + 5 portal permissions), roles per tenant in `tenant_roles` that the Owner can edit or create at Pengaturan → Peran & Akses, each with a project scope (`all` / `assigned`). The backend checks `Grants.Can(key)` per request (`middleware.LoadGrants`); the web mirrors it with `useCan` / `RequirePermission`. Client roles (**Pengantin**, **Keluarga**, or custom) decide what the portal shows. |
| **Pengaturan** | The WO Console sidebar's collapsible settings group — `Pengguna`, `Peran & Akses`, `Langganan`, `Kategori Vendor`, `Timeline Default` — collapsed by default. Each entry appears only for roles holding its permission (`team.manage`, `role.manage`, `subscription.manage`, `vendor.category.manage`, `template.manage`); by default only the Owner. |
| **WO Console** | The tenant-facing app surface (`/dashboard`, `/projects`, `/clients`, `/vendors`, `/vendor-categories`, `/venues`, `/pengguna`, `/langganan`, `/timeline-default`). |
| **Platform Console** | ElProof's own internal admin surface (`/platform/*`), used by ElProof staff (`platform_admin`), never by tenants. |
| **Client Portal** | Read-only surface (`/portal/*`) for a wedding's bride/groom/family to track their own project — five tabs (Vendor, Timeline, Pembayaran, Kendala, **Dokumen**, ADR-0020), Dokumen appended last since it's a newer, separate, opt-in capability rather than a reordering. |
| **Principal** | Whoever is authenticated: `staff` (WO Console), `client` (Client Portal), `platform_admin` (Platform Console), or `app` (an external SaaS consumer of `payment`'s Fase 10 API, minted via `POST /auth/app/token` — no `credentials` row, no refresh token). See ADR-0005 and its update. |
| **App** (payment) | A consumer registered in `payment`'s App registry (`payment_apps`), allowed to create charges through ElProof's one gateway wallet. `kind=internal` (in-process, e.g. `platform-billing` — ElProof's own subscription billing) or `kind=external` (HTTP, another SaaS product, managed via Platform Console's "Manajemen Aplikasi"). Not to be confused with the `App` React component or "application" in a general sense — always refers to this registry concept. See `MODULE_PAYMENT.md`. |
| **Konfigurasi Gateway** | Platform Console page (`/platform/pembayaran`) for choosing the active payment provider (Tripay) and its sandbox/production credentials — write-only, never echoes a stored secret back. |
| **Manajemen Aplikasi** | Platform Console page (`/platform/aplikasi`) for registering/managing external Apps (see above) — reveal-once secrets, reset, toggle active/inactive. |
| **Reconciliation sweep** | `payment`'s background safety net (`ReconcilePending`) for a charge whose webhook was never received — periodically re-checks still-open charges directly against the gateway and force-resolves anything left open long past its own expiry. See `MODULE_PAYMENT.md` §6 step 6. |
| **Project** | One wedding engagement managed by a tenant. Has a lifecycle status (`Draft→Preparation→Ready→Completed`/`Cancelled`) that changes only through explicit actions (`/transition`, `/cancel`), never by editing the project — ADR-0027 and owns Timeline items, vendor engagements, payments, issues, evidence, activity — plus at most one attached **Venue** (`venue_id`, ADR-0016). Also has an `is_archived` flag, orthogonal to status (reversible, any staff role) — and can be permanently hard-deleted (Owner-only, requires already archived or cancelled first) — see ADR-0013. Can also be **duplicated** into a brand-new project, cloning its Timeline and vendor lineup (with each vendor's pricing tier) as a reusable template (payments/issues/evidence/activity/clients are never copied) — see ADR-0014. Only Owner/Admin create or duplicate a Project, or reassign its PIC — see **RBAC** above. |
| **Timeline** (Project Timeline) | The wedding's own top-level checklist — display label only; the underlying identifier, DB table (`project_milestones`), and API shape are still "milestone" everywhere (deliberate, display-text-only rename). Seeded into every new project from that tenant's own **Timeline Default Template**, not a single list shared by every tenant. |
| **Tanggal Booking** | Display label only — the underlying identifier/column/API field is still `prepStartDate`/`prep_start_date` everywhere (deliberate, display-text-only rename, same convention as **Timeline** above). Feeds the dashboard's "Progress Tertinggal" lagging calculation and new-project Timeline seeding exactly as before; only the label changed. |
| **Timeline Default Template** | A tenant's own configurable checklist (name + a signed day-offset per item), managed from Pengaturan → Timeline Default (Owner-only), auto-copied into a new project's own Timeline the moment it's created. Replaces what used to be one hardcoded 6-item list shared by every tenant. An item's offset can be positive ("H-", before the event) or negative ("H+"/"Setelah Acara", after it — e.g. returning the seserahan box a few days post-event); the form presents this as a Sebelum Acara/Setelah Acara toggle, not a signed number field. A newly registered tenant gets the same starter 6 H- items seeded automatically; editing the template afterward never retroactively changes any already-created project's Timeline, and has no effect on Duplikat Project (which clones the *source project's* actual Timeline, not the tenant's current template). |
| **Project Vendor** | The engagement between a Project and a Vendor (scope, contract value, DP/paid amounts, status, pricing tier) — not the Vendor record itself. |
| **Pricing Tier** (`pricingTier`) | Which of a Vendor's own two preset prices (`priceAkad`/`priceAkadResepsi`) a Project Vendor engagement's contract value was auto-filled from when created/edited — "Akad Saja" or "Akad + Resepsi," picked per engagement (not once for the whole project, since different vendors on the same project can legitimately have different scopes). Purely a stored label: the engagement's own contract value stays freely negotiable and is never re-derived from it afterward. |
| **Margin** (Margin/Keuntungan) | A project's contract value minus every cost sourced for it — the sum of every non-Cancelled Project Vendor's contract value, minus the attached Venue's rental price + charge (0 if none attached). Computed client-side on the fly, never stored. Shown only to Owner/Admin on the Project header — hidden from Wedding Planner, since it reveals vendor/venue cost data that role isn't otherwise allowed to see. |
| **Vendor Milestone** (Timeline Vendor) | A checklist item tracked against one Project Vendor engagement (distinct from a Project's own Timeline). Same display-text-only rename as Timeline above — `vendor_milestones` table/identifiers unchanged. |
| **Venue** | A bookable wedding location — its own directory (ADR-0016), still inside the `vendors` module but not a vendor category. Carries fields a generic vendor doesn't (mandatory rental price, a separate charge, capacity, facilities, a single document/photo attachment) and attaches to a Project 1:1 (`projects.venue_id`), never through a `project_vendors`-style engagement — no per-project negotiated price/DP/paid-amount tracking for it. Commercial fields (rental price, charge, PIC contact) are staff-only; Client Portal sees only the public-safe subset, shown as a pinned card inside the Vendor tab rather than its own tab (ADR-0016's Revision). Can also be permanently hard-deleted (Owner-only, informed-consent — ADR-0018), same guardrail model as Vendor/Pengguna. |
| **Evidence** | An uploaded document/photo attached polymorphically to a vendor milestone, vendor payment, project vendor (engagement), issue, client payment, or venue payment (`relatedKind` + `relatedId`) — six kinds, all unconditionally visible to a `client` principal the moment they're attached to something inside their own project. A 7th kind, **`general`** (ADR-0020), is a standalone document with no such context (`relatedId` a sentinel `0`) — the only kind with a per-document Client Portal visibility toggle (`isClientVisible`, default hidden), surfaced via Client Portal's own **Dokumen** tab. Vendor/client/venue payments can now also be edited or hard-deleted (see **Pembayaran** below); deleting one cascades to its own evidence rows first. |
| **Pembayaran** (payment ledgers) | The three payment tables inside a project — vendor payments (money out to a vendor), client payments (money in from the client, "Uang Masuk dari Client"), and venue payments (money out to the venue). Each row can be edited (full-field, no role gate) or hard-deleted (**Owner-or-Admin** — see ADR-0019, the only hard-delete in this codebase that isn't Owner-only); deleting cascades to that payment's own **Evidence** rows first. A payment row's attached evidence can be viewed inline from its own tab via "Lihat Bukti," without leaving the tab. |
| **Granted (transaction status)** | A subscription transaction created by Platform Console manual activation — bypasses payment, deliberately excluded from paid-revenue reporting. Distinct from `paid` (real payment). |
| **Plan (Subscription Plan)** | A row in the shared plan catalog (`billing` module) — name, duration, price, feature list. Single source of truth rendered identically on the WO Console's `Langganan` card and the Platform Console's `Paket` CRUD. |
