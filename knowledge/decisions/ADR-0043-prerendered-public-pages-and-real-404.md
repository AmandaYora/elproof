# ADR-0043: Prerendered public pages, sitemap, and a real 404

## Status
Accepted — implemented 2026-11-15 (QA finding EP-13). Extends ADR-0038 (public site); the consoles are unchanged.

## Context
QA (EP-13) fetched the raw HTML of every public URL: each answered the same empty shell titled "ElProof — Portal
transparansi klien", `/sitemap.xml` answered the app, any made-up URL answered 200, and no page had a canonical link.
The site is a Vite SPA served by the Go API (`spaFileServer`, one container behind host nginx); titles and descriptions
were set only at runtime by `usePageMeta`, so crawlers and link previews that run no JavaScript saw none of it.
Constraints: no Node server in production (one Go binary), the entry chunk budget (ADR-0037), prices come from the API at
runtime (ADR-0038), and the public pages are lazy routes of the same router as the consoles.

## Decision

### Build-time prerender of the public pages, hydrated in the browser
* `app/routes/public-pages.ts` (`PUBLIC_PAGES`) is the one list of prerendered pages with their title, description and
  `noindex`: Beranda, Tentang Kami, FAQ, Kontak, the four legal pages, Daftar and Masuk. Each page passes its entry to
  `usePageMeta`. Siapkan workspace and Undangan are left out: they need a Google credential or a token, are `noindex`,
  and the shell serves them.
* `npm run build` = `tsc -b && vite build && npm run prerender`. `prerender` builds `src/entry-server.tsx` for Node
  (`vite build --ssr`, output `dist-ssr/`, not shipped) and runs `scripts/prerender.mjs`, which renders each page with the
  real route table (`app/routes/routes.tsx`, shared with the browser router) in a memory router, and writes
  `dist/prerendered/<page>.html`: the built shell with the page's `<title>`, description, `robots` (Masuk), canonical +
  `og:url` (indexable pages), Open Graph and Twitter tags, `data-surface="marketing"` on `<html>`, and the markup inside
  `<div id="root" data-prerendered="<path>">`.
* Rendering is two passes: `prerender` (react-dom/static) waits for every lazy chunk, then `renderToString` writes the
  page in document order. A single `prerender` pass writes Suspense content out of order behind inline `$RC` scripts
  (React 19.2), which a strict Content-Security-Policy blocks and which wait for `requestAnimationFrame`; the script
  fails the build if the markup still has an inline script or a pending boundary.
* `main.tsx` calls `hydrateRoot` when `#root[data-prerendered]` equals the opened path (trailing slash ignored), and
  `createRoot` otherwise. Hydration was chosen over replacing the markup with `createRoot`: `createRoot` would first show
  the router's Suspense fallback (an empty main area) until the page chunk loads, and lose scroll position; with
  `hydrateRoot` React keeps the server markup while lazy chunks load and adopts it, and a part that differs (a sign-in
  page restored with history state) is re-rendered in the browser, logged with `console.warn`, never broken.
  Verified in a browser: the server-rendered nodes are the ones on screen after hydration, no warning on any page.
* What a public page renders first must not depend on the browser: the "Cara kerja" story reads the viewport through
  `useMediaQuery` (server snapshot = phone layout), the price list starts in its loading state, Daftar reads `?paket=`
  in an effect. `theme/tabIdentity.ts` no longer reads `document` at module load. The prerendered HTML carries no
  inline script and no `style` attribute (`ProofSeal`'s transform origin is a class), so a strict CSP does not change it.
* Prices are not prerendered: Beranda's HTML carries the price section's loading state; the browser fills it from
  `GET /api/v1/public/plans` as before. The head tags are complete without them.
* `SITE_URL` (`shared/constants/site.ts`) is `VITE_SITE_URL` at build time, default `https://elproof.elcodelabs.com`;
  it is the base of canonical links, `og:url`, sitemap entries and the robots `Sitemap:` line.

### sitemap.xml and robots.txt
The prerender writes `dist/sitemap.xml` with the indexable pages of `PUBLIC_PAGES` (not Masuk) and appends
`Sitemap: <SITE_URL>/sitemap.xml` to `dist/robots.txt` (`public/robots.txt` stays without a host).

### The Go server answers 404 for unknown paths
* The prerender also writes `dist/routes.json`: `pages` (public path → prerendered file) and `routes`, every path pattern
  of the React router, generated by walking `app/routes/routes.tsx` (the catch-all `*` excluded), so it cannot drift.
* `spaFileServer` (`apps/api/cmd/server/spa.go`) reads it once at start-up and answers, in order: `/api/*` → JSON 404;
  `/routes.json` and `/prerendered/*` → 404 (reachable only by their public path); a public path → its prerendered file;
  an existing file → the file (`sitemap.xml` as XML); a router path (literal segments case-insensitive, `:param` one
  segment, `x?` optional, `*` rest, like react-router) → the shell with 200; anything else → the shell with **404**, so
  the not-found page shows and crawlers get a real 404. HTML is sent with `Cache-Control: no-cache` (it names the hashed
  assets of its build).
* Without `routes.json` (a Vite dev build, an older image) or with an unreadable one, the server keeps the old behaviour
  (the shell with 200 for every path), so a missing file can never turn the whole app into 404s.

## Consequences
* Crawlers and link previews read each public page's own title, description, canonical and content without JavaScript.
* A new public page is one entry in `PUBLIC_PAGES` plus its `usePageMeta(PUBLIC_PAGES.x)`; a new route of any kind
  needs nothing on the server.
* Public pages must keep their first render browser-independent, or React re-renders the differing part in the browser
  (correct, but a wasted render and a console warning).
* The build takes a few seconds longer; the image still copies `dist/` as is (`infra/docker/Dockerfile` unchanged).
* The e2e stack builds with `vite build` only, so the browser tests keep exercising the plain client render; the
  prerendered path is covered by `scripts/prerender.mjs`'s own checks and `spa_test.go`.
* Old `/homepage/*` links still answer 200 and redirect in the browser; a server-side 301 is not part of this change.
